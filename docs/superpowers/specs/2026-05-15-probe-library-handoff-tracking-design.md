# Design — probe-library handoff, progress tracking, and install improvements

**Date:** 2026-05-15
**Status:** approved-for-planning

## Problem

The probe-feature skill library is a long chain (`shape-feature` → `probe-feature`
→ `slice-issues` → `sequence-issues` → `execute-issue` → `verify-issue` →
`publish-issues`). Three problems make it easy to get lost:

1. **Handoffs are not copy-pasteable.** Most SKILL.md files end with a
   `> "...Next: \`...\`"` line, but they use placeholders (`<NNN>`,
   `001-...`) or name a skill with no slug. The user cannot paste them.
2. **Bare issue numbers are ambiguous.** `/execute-issue 005` can resolve to
   the wrong feature's issue 005 because issues live per-feature and nothing
   disambiguates. There is also no feature-level notion of "done" — completion
   is implicit in each issue's Execution log / Review verdict.
3. **Install scripts prompt one-at-a-time.** `install.ps1` / `install.sh`
   prompt per-skill on collision with only a blunt `--force`/`-Force`
   (overwrite-all). No skip-all or archive-all, no single up-front choice.

## Scope

In scope: STATUS.md progress tracker, slug disambiguation, literal
next-command emission across the chain, slug-as-argument consistency, install
script global-choice + flags.

Out of scope (YAGNI): global cross-feature index; auto-closing GitHub issues;
changing issue numbering; any `publish-issues` change beyond accepting a slug
argument.

## Part A — STATUS.md per-feature progress tracker

**File:** `docs/features/<slug>/issues/STATUS.md`

**Ownership:**
- `slice-issues` — seeds it (writes the full table, all cells `—`).
- `execute-issue` — sets the `Executed` cell for one issue.
- `verify-issue` — sets the `Verified` cell for one issue.
- `sequence-issues` — **reads** it to compute the next item; **never writes** it.

**Format:**

```markdown
# Status — <feature name> (<slug>)

Generated by slice-issues; updated by execute-issue / verify-issue.
Do not hand-edit the table. The Notes section is yours and is preserved.

| Issue            | Slice    | Executed   | Verified         |
|------------------|----------|------------|------------------|
| 001-add-webhook  | vertical | 2026-05-15 | 2026-05-15 PASS  |
| 002-retry-queue  | vertical | —          | —                |

**Feature status:** in-progress — 1/2 executed, 1/2 verified

## Notes
<freeform; preserved across regenerations>
```

**Cell rules:**
- `Executed`: `—` until executed; then `<YYYY-MM-DD>`. If the subagent
  reported `BLOCKED` or `NEEDS_USER`, append the status:
  `2026-05-15 BLOCKED`.
- `Verified`: `—` until verified; then `<YYYY-MM-DD> <VERDICT>` where VERDICT
  is `PASS` / `FAIL` / `NEEDS_USER`.
- **Feature status** line recomputed on every update: `in-progress — X/N
  executed, Y/N verified`, becoming `complete` when all rows are verified
  `PASS`.
- **Self-heal:** if STATUS.md is missing when `execute-issue` or
  `verify-issue` runs (pre-existing feature predating this change), regenerate
  it from each issue's Execution log / Review verdict sections, then proceed
  with the normal update.
- The `## Notes` section is never overwritten by any skill.

## Part B — Slug disambiguation

Applies to `execute-issue` and `verify-issue` "Resolve target issue" step.
Argument resolution rules, in order:

1. Argument contains `/` or is an existing path → use directly
   (e.g. `payments-v2/003-add-webhook`, or a full path).
2. Bare `NNN` or `NNN-name` → glob `docs/features/*/issues/NNN-*.md`:
   - 0 matches → abort: "No issue `NNN` found under `docs/features/`."
   - exactly 1 match → use it.
   - **>1 matches → HARD STOP.** Print every candidate as a fully-qualified
     command (`/<skill> <slug>/<NNN-name>`) and require the user to re-run
     with the disambiguated form. Never guess.

## Part C — Literal next-command emission across the chain

Every chained skill's final report emits **slash-prefixed, fully-qualified,
copy-pasteable** commands with the resolved slug. Fan-outs list all applicable
commands; conditionals list each branch with its condition.

| Skill | Emitted next command(s) |
|-------|--------------------------|
| `shape-feature` | `/probe-feature <slug>` |
| `probe-feature` | `/slice-issues <slug>` |
| `probe-product` (standalone) | `/probe-design <slug>` **and** `/probe-technical <slug>` (both required before write-prd) |
| `probe-design` (standalone) | remaining probe(s) if any, else `/write-prd <slug>` |
| `probe-technical` (standalone) | remaining probe(s) if any, else `/write-prd <slug>` |
| `write-prd` | `/write-design-brief <slug>` **and** `/write-tech-spec <slug>` |
| `write-design-brief` | `/write-tech-spec <slug>` |
| `write-tech-spec` | `/slice-issues <slug>` |
| `slice-issues` | `/sequence-issues <slug>` |
| `sequence-issues` | `/execute-issue <slug>/<first-unexecuted NNN-name>` (computed from STATUS.md + sequence order) |
| `execute-issue` | DONE → `/verify-issue <slug>/<NNN-name>`; BLOCKED/NEEDS_USER → fix, then re-run `/execute-issue <slug>/<NNN-name>` |
| `verify-issue` | PASS → `/execute-issue <slug>/<next-unverified NNN-name>` (next in SEQUENCE order per STATUS.md), or `/publish-issues <slug>` if all verified; FAIL → fix, then `/verify-issue <slug>/<NNN-name>` |

**Orchestration unchanged:** `probe-feature` remains the front door. It
invokes `probe-product` → `probe-design` → `probe-technical` sequentially
behind the scenes (its step 2), threading the resolved slug into each
sub-skill so they never re-ask. The standalone "Next:" lines added to the
three probe sub-skills only apply when a user invokes them directly outside
the orchestrator.

**Supporting consistency fix — slug as argument:** every skill that *emits*
`/<skill> <slug>` must *accept* the slug as an optional first argument. Today
these skills only ask for the slug interactively. New behavior: documented
optional first argument; if absent, fall back to asking as before. Affected:
`probe-feature`, `probe-product`, `probe-design`, `probe-technical`,
`write-prd`, `write-design-brief`, `write-tech-spec`, `slice-issues`,
`sequence-issues`, `execute-issue`, `verify-issue`, `publish-issues`,
`shape-feature`.

## Part D — Install scripts: up-front global choice + flags

Both `install.ps1` and `install.sh`:

- **New non-interactive flags:** `--overwrite` / `--skip` / `--archive`
  (sh) and `-Overwrite` / `-Skip` / `-Archive` (ps1). `--force` / `-Force`
  retained as an alias for overwrite (back-compat). Flags are mutually
  exclusive — validate and error on conflict.
- **Interactive global choice:** on the **first** collision, ask once:
  `overwrite-all / skip-all / archive-all / decide-each`. `decide-each`
  falls back to today's per-skill `o/s/a` prompt. Any `-all` choice (or a
  flag) is remembered for the rest of the run; no re-prompting.
- `--dry-run` / `-DryRun` continues to compose with all of the above.
- The existing prototype-archive prompt (probe/scope/grill-me) is unchanged.

## Testing

This is a skills/scripts repo (Markdown + shell/PowerShell), so testing is
primarily manual verification:

- **STATUS.md lifecycle:** run slice-issues on a sample feature → STATUS.md
  seeded with all `—`. Run execute-issue → one Executed cell set. Run
  verify-issue → one Verified cell + verdict set, feature-status line
  recomputed. Re-run sequence-issues → STATUS.md untouched.
- **Self-heal:** delete STATUS.md for a feature with filled Execution
  logs; run execute-issue → STATUS.md regenerated from existing logs.
- **Disambiguation:** create two features each with an issue `005`; run
  `/execute-issue 005` → hard stop listing both fully-qualified commands.
  Run with `slug/005-name` → resolves cleanly.
- **Next-command emission:** spot-check each chained skill's final report
  renders a literal slash command with a real slug (no `<NNN>` / `...`).
- **Install scripts:** with a populated `~/.claude/skills/`, run installer
  interactively → first collision asks the 4-way global question; choose
  skip-all → remaining collisions skipped without prompts. Run with
  `--archive` / `-Archive` → all collisions archived non-interactively.
  Run with two collision flags → exits with a clear error. `--dry-run`
  composes with each.
